# DOC-09 Security & Authorization Policy

## Roles and authorization
`chief_admin`: company-wide account and administrator-authority management, subject to self-role/self-scope modification denial. `standard_admin`: account provisioning, status management, and session revocation for `employee` targets in explicitly granted departments only; never creates, changes, delegates, revokes, or otherwise manages administrator authority. `employee`: own profile/session, member conversations, own tasks/metrics, and own briefing; no administrator API access. Every administrator request resolves current role and department scope from PostgreSQL; IDs or role/scope claims supplied by the client are not authority. Missing/inactive role, missing scope, self-modification, cross-department target, or unsupported role/target pairing fails closed. Service scheduler: task automation only. AI gateway: filtered briefing input and summary output only; no account, message mutation, task mutation, or unrestricted DB credentials. Enforce access in API/DB query scope, never only UI.

## Administrator authorization matrix
| Operation | chief_admin | standard_admin | employee |
|---|---|---|---|
| Create, read, deactivate, or revoke sessions for an employee account | Company-wide | Only employee target in an explicitly granted department | Deny |
| Designate or revoke a standard administrator | Allowed; cannot alter own role | Deny | Deny |
| Grant or revoke a standard administrator's department scope | Allowed; cannot alter own scope | Deny | Deny |
| Manage a chief administrator account | Company-wide, except caller's own role/scope | Deny | Deny |

Role/scope changes lock affected authorization rows, use database uniqueness/FK constraints, increment affected authorization state, revoke affected sessions/token families, and write before/after audit records in one transaction. This prevents role-ID guessing, horizontal/cross-department bypass, stale authorization, concurrent modification races, and inactive-administrator access. WebSocket authorization reuses the current server-side session and authorization validation rather than trusting a stale client state.

## Authentication and session
No public registration. Password hashing uses Argon2id and first login forces password change. Access tokens expire in 15 minutes; refresh tokens expire in 7 days. PostgreSQL is the session store. The server stores only a hash of each refresh token, rotates it atomically, and detects presentation of a consumed/replaced token. Reuse detection revokes the whole token family and active sessions; concurrent refresh has one atomic winner and the losing/replayed request is rejected. Logout and administrator revocation invalidate applicable sessions. Account disable increments auth version, revokes all sessions/families, rejects later API access, and terminates WebSockets. Login errors never disclose account existence. Initial administrator creation is ONE_TIME_LOCAL_CLI only: approved operator performs local execution, supplies the cryptographically random secret and initial password interactively, and CLI compares the input to a separately configured local-environment approved secret. Secrets are never CLI arguments, logs or database values and are discarded after successful bootstrap. PostgreSQL transaction, advisory lock and singleton constraint provide atomic one-winner bootstrap, audit record and fail-closed reexecution. Never log passwords, access tokens, refresh tokens, or their raw values.

## Data protection, audit, and AI
TLS protects in transit; encryption-at-rest/key management and retention require operations approval. Audit account/permission changes and sensitive administrative queries with actor/time/target/result. Briefing selection rechecks user authorization; summaries contain source message IDs and deep links. Provider selection, data minimization, retention, region, model and spend ceiling are blocked until ADR-007. AI cannot change read or task state.

## Threat controls
Validate schemas and file metadata; parameterize queries; constrain WebSocket origin/rate/message size; use CSP and Tauri least-privilege capabilities; rate-limit login/search/briefing; patch dependencies; use correlation IDs without secret content. Attachment malware scanning is required; scanner product and retention are OPEN under OD-001. Security acceptance maps to AT-AUTH-03/04, AT-MSG-05/07, AT-AI-01/03/05, AT-TASK-07/08 and AT-NFR-01/05/06.

## R2 approved-policy clarification
Passwords use Argon2id and first login forces a password change; OD-002 fixes 15-minute access and 7-day refresh lifetimes, hash-only refresh storage, rotation/reuse detection, PostgreSQL sessions, and REST/WSS session validation. Chief administrators have company account-management scope; standard administrators have explicitly delegated-department scope, with audit records for authority changes and sensitive queries. AI may receive only minimum necessary unread messages in accessible work rooms and must return source linkage; retention and external-transfer notice are OPEN. Private R2 objects require backend authorization and passed malware scanning. Tauri automatic update verification requires valid signatures. Scanner product/retention and update distribution/signing operations remain OPEN.
