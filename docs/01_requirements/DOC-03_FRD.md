# DOC-03 Functional Requirements Document

## Authentication flows
Admin submits a staff identity record to `AUTH-001`; server checks administrative scope, creates an active account in change-required state, safely delivers its initial credential out-of-band, and writes an audit event. Public registration does not exist. The first administrator uses ONE_TIME_LOCAL_CLI only: an approved operator enters the cryptographically random one-time secret and initial password interactively, while the CLI reads a separately configured approved secret from the local environment. The secret is not a command-line argument, log value, database value, or shared automatic source; comparison is followed by PostgreSQL transaction/locking/constraint single-winner control. Account creation, consumed bootstrap state and audit record commit atomically; any failure rolls back and any reexecution fails closed. Login (`AUTH-002`) uses Argon2id verification and generic failure responses. First login issues no normal access token until password change completes. After success, access tokens expire in 15 minutes and refresh tokens in 7 days. Refresh (`AUTH-003`) consumes and replaces one hash-stored refresh credential atomically; reuse or concurrent double-use revokes its token family and sessions. Logout, administrator revocation, and account disable revoke sessions; disable also increments auth version and closes active sockets. REST and WebSocket operations validate account/session status. Every authority and authentication-security change uses `AUTH-004` audit fields without recording password or raw token content.

## Messaging flows
Client posts a message then receives durable acknowledgement (`MSG-001`, `MSG-003`), followed by WebSocket delivery to current authorized participants. Group membership (`MSG-002`) is checked on both history/read and live delivery. A reconnect presents last durable event cursor (`MSG-004`); server returns ordered authorized events or requires REST pagination. Search, receipts, attachments and OS integration follow `MSG-005`–`MSG-008`; attachment content storage and retention remain pending Owner policy.

## Morning briefing flows
On first local-day activation, client requests briefing. Server resolves the user/timezone and unread authorized range, ranks message signals, creates source-linked response, and records non-content operational metadata. AI only receives the filtered authorized range. `AI-003` forbids state mutation. If timeout, provider rejection, or unavailable service occurs, `AI-004` returns the source unread list. Same user/range/prompt version may reuse an access-controlled cache (`AI-005`).

## Task flows
Employee creates and checks only their tasks (`TASK-001`, `TASK-002`). A server scheduler consults approved calendar rules and creates a new carryover instance linked to `root_task_id`, retaining original creation date (`TASK-003`). Recurrence is idempotent through a unique tuple (`TASK-004`). Missing calendar data produces an operational error (`TASK-005`), never guessed dates. Metrics are a server calculation over check history (`TASK-006`); administrator filter scope is enforced at query time (`TASK-007`). AI holds read-only briefing scope only (`TASK-008`).

## R2 approved-policy clarification
Attachments are private Cloudflare R2 objects and remain unavailable until the malware-scan gate passes; retention and scanner product are OPEN. Korean public holidays plus administrator-designated days off are the shared calendar input for carryover, recurrence, and task-calendar display. Chief administrators operate company-wide account management; standard administrators operate delegated departments. The briefing filter is unread messages only in work chat rooms accessible to the requester, with minimum necessary transfer and source links. Notification, tray, signed-update verification, Windows installation, and auto-start have separate acceptance contracts in `MSG-008`, `WIN-001` through `WIN-003`. OD-002 authentication token/session policy is accepted in SM-R01-B-R0; AI retention/notice, attachment retention/scanner product, and update distribution/signing operations remain implementation gates.
